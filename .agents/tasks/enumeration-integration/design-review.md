# Design Review: Enumeration Integration

## Findings

1. **HIGH — `/review/test` integration is not concretely grounded in the current route/navigation source.** The design says to add `apps/web/app/(app)/review/test/[quizId]/page.tsx`, copy the contract from `practice/[quizId]`, and update a “reviewer/test navigation symbol” identified during implementation. Targeted source inspection found the existing flashcard route at `apps/web/app/(app)/review/[quizId]/page.tsx`, practice links in `QuizStartConfigModal.tsx`, and no `/review/test` route or existing reviewer/test navigation symbol. The design therefore leaves the loading/authorization implementation and the actual navigation integration point to discovery during coding, while the requirement explicitly requires a concrete, verified adaptive route. **Fix:** name the exact existing practice page and exact navigation component/file to change, specify whether `/review/test/[quizId]` is a new sibling route or `/review/[quizId]` is changed, and provide the route test’s exact request/expected marker for owner, shared, subject-shared, legacy, and missing cases. If no navigation entry exists, explicitly add one to the named component rather than saying it will be identified later.

2. **HIGH — The design does not define a safe integration boundary for `useQuizSession`’s current single-answer transition pipeline.** The current hook stores one `selectedOptionId`, one typed input/result, and `answerQuestion()` immediately records telemetry, mastery, queue transition, pending advance, and completion state for each submission. The design says enumeration actions “do not invoke the ordinary transition after the first selection” and then call `calculateAnswerTransition` once at quota completion, but it does not specify how the hook prevents existing renderer calls, resets `isEvaluating`, manages `pendingAdvance`, or preserves the active question while intermediate feedback is shown. This is a feasibility gap that can produce a transition on the first term or leave the question stuck evaluating. **Fix:** define concrete hook action signatures and lifecycle rules, for example: `submitEnumerationTerm(value): void` records only enumeration state while `status === active`; at completion it atomically sets `isEvaluating`, `answerResult`, and `pendingAdvance` from the final verdict and invokes `calculateAnswerTransition` exactly once; `advance()` remains the only path that clears the active state. State that `QuizQuestionRenderer` must not call `answerQuestion`/`submitTypedAnswer` for enumeration.

3. **HIGH — Retry/re-presentation semantics for enumeration attempts are unspecified.** The design persists `enumerationByQuestionId` and says a changed question/quota/key clears a record, but it does not say when a completed or wrong enumeration record is cleared when mastery puts the question into the struggle pile and presents it again. Reusing the record would make the re-presented question already complete; clearing it without defining the event can lose partial progress on ordinary navigation. This conflicts with the requirement to preserve mastery behavior and support saved partial progress. **Fix:** specify a lifecycle key such as `(sessionId, questionId, presentation/attempt number)`, and state that a new queue presentation starts a fresh enumeration state while reload of the same presentation restores it. Define whether a completed attempt is retained only for recap/history or removed from active state, and add a test for wrong completion followed by struggle retry.

4. **MEDIUM — Persistence and DTO scope is named broadly but not made implementable.** “All relevant DTOs,” “API schemas,” “database schema/migration,” and “every repository row mapper/serializer” do not identify the actual files or storage representation. The current `QuizQuestion` type has no fields, and `QuizQuestionInput`/update DTOs likewise expose only `options`; the review cannot determine whether SQL uses JSON, separate columns, or a migration mechanism. **Fix:** list the exact DTO, API route/schema, SQL migration, and each repository mapper, and specify the database column type/default/null behavior for both arrays. Include a round-trip assertion that distinguishes missing/null, valid `[]`, and malformed persisted values.

5. **MEDIUM — Canonical identity and distractor collision rules are not fully deterministic.** The design says terms use `areAnswersEquivalent`, gives each a normalized identity key, and says distractor identity is distinct from canonical identity, while also saying duplicate canonical terms/distractors are removed. It does not define whether a distractor equivalent to a canonical term is dropped, how Unicode/case/whitespace normalization becomes a stable key, or how a canonical term and distractor with the same display text are assigned IDs. This can make duplicate suppression and final correctness differ between modes. **Fix:** define one exported `getAnswerIdentityKey()` based on the exact core equivalence policy; deduplicate canonical terms first; remove any distractor whose key is in canonical keys; deduplicate remaining distractors by the same key; derive option IDs from ordered kind plus index; test case/whitespace-equivalent collisions.

6. **MEDIUM — The quota rule is not fully reconciled with explicit `answer_terms` when legacy `options` is populated.** The table says a positive `answer_text` differing from the non-empty legacy option count derives `total = N`, while `answer_terms` supplies the canonical terms. If `answer_terms` has a different count from `options`, the design only indirectly reaches `insufficient_terms`; it does not state whether a larger explicit term list is truncated, whether a smaller list is always unavailable, or whether the legacy count is still authoritative after migration. **Fix:** state explicitly: for non-empty legacy options, `total` is the count of non-empty options regardless of `answer_terms`; canonical terms are never truncated; fewer than `total` unique canonical terms is unavailable; more than `total` terms is either an invalid key or has a specified first-N rule. Add each case to the decision-table tests.

7. **MEDIUM — Privacy handling for the new canonical fields is asserted but not specified at the payload boundary.** The design requires public answer-key privacy and says fields are added to public/internal DTOs, but it does not identify where public question serialization strips `answer_terms` and `enumeration_distractors`, nor how the client can render a hidden-key flashcard without receiving the terms. Adding both fields to a “public/internal question DTO” could leak the complete key before the component guard runs. **Fix:** define separate owner/internal and public/shared DTO projections, explicitly omit both fields from the public payload when `canViewAnswerKey` is false, and test serialized response and rendered markup—not only the component output.

8. **NIT — The design’s test plan says to run builds/typechecks and browser smoke tests although the review request excludes rerunning tests.** This is not a design blocker, but it mixes implementation execution into the design plan. **Fix:** keep those as implementation acceptance steps and identify the exact route/runtime test command separately; do not treat a design review as having verified them.

## Verified Assumptions

- `QuizQuestionType` currently contains `multiple_choice`, `typed_answer`, and `enumeration`; `QuizMode` already contains `learn` and no combined mode.
- `getQuestionAnswer()` currently returns the numeric enumeration value, using the non-empty `options` count unless a valid numeric `answer_text` matches it or options are empty.
- `areAnswersEquivalent` is imported from `@quiz-creator/core` by `apps/web/lib/quizAnswerEvaluation.ts`.
- `QuizQuestion` currently has `options` and `answer_text` but no `answer_terms` or `enumeration_distractors`; the visible DTO definitions likewise do not contain these fields.
- `useQuizSession` currently has one `selectedOptionId`, typed-answer state, and an `answerQuestion()` path that immediately records telemetry and calculates a mastery transition.
- The current source has `apps/web/app/(app)/review/[quizId]/page.tsx` and practice navigation links, but targeted source search found no `/review/test` route or link.
- `FlashcardReview` currently has a single-answer helper that prefers `answer_text` and then one option, so it does not render an enumeration term list.

## Unverified/Wrong Assumptions

- The design assumes a reviewer/test navigation component exists; targeted source inspection did not verify such a symbol. The exact navigation entry point and required change remain unverified.
- The design assumes the practice page’s loading contract can be copied to the new route, but the actual practice page source and route helper contract were not established by the design itself; implementation must name and inspect them before coding.
- The design assumes adding answer fields to public/internal DTOs is compatible with existing privacy serialization. No source-backed proof of that projection or omission behavior is provided.
- The design assumes the current mastery/session architecture can support intermediate enumeration submissions without changing queue/evaluation state, but the existing hook’s immediate-transition behavior shows that this requires an explicit adapter/state boundary.

## Verdict

**CHANGES_REQUESTED** — 7 HIGH/MEDIUM findings block approval.
